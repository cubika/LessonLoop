# 实现质量评估

日期：2026-09-14。状态：实现与评审规范。本文补充场景合同、判定方法和评测门禁；已同步首批开发材料及完整性校验，产品质量评测入口与 CI 尚未按本文实现。现有命令和缺口见文末。

每项功能都要能回答：给定哪些材料和状态，系统应做什么，哪些行为算失败，结果由谁或什么程序判定。验收 ID、发布样本规模和阈值统一维护在[实施与验收](05-delivery-and-validation.md)，本文不另设一套发布分数。

## 分开评价四类质量

| 方面 | 要判断的结果 | 主要证据 | 通过的含义 |
|---|---|---|---|
| 行为正确性 | 授权、适用性、修订、来源失效、写入恢复和回执符合合同 | 确定性测试、真实后端集成、故障注入 | 当前配置下列明的合同成立；关键违规不能被平均分抵消 |
| 经验质量 | 留下有用发现，保留条件和例外，结论得到来源支持 | 固定材料、独立标签、逐项语义判定 | 覆盖与噪声同时达标；字段合法、摘录存在只证明结构正确 |
| 后续任务收益 | 正确完成任务，减少重复调查和纠正 | 隔离任务对照、实际文件与工具结果、重复运行 | 相同条件下观察到有限范围的收益；召回命中不能单独证明收益 |
| 运行与使用质量 | 安装可用、延迟受控、失败可见、重启后恢复、纠正确实生效 | CLI/UI/Copilot 端到端操作、性能与恢复记录 | 声明的平台和规模通过；本地脚本探针不能代替真实宿主体验 |

分别报告这四类结果。代码覆盖率可用来找遗漏路径，经验条数、L5 比例和模型自评分只作诊断，不作为完成标准。

## 从验收要求到场景合同

实现一个功能前，先选择相关验收 ID，补齐能决定通过或失败的场景。已覆盖的行为复用现有测试；只为新增行为或发现的漏洞增加断言。每个场景按以下字段保存，字段属于开发评测资料，不进入产品 API。

| 字段 | 必填内容 |
|---|---|
| 身份与范围 | 稳定 scenarioId、family、版本、关联验收 ID、所属阶段、适用 profile、必测或诊断、责任人 |
| 来源与划分 | 手写机制样本或获准使用的脱敏材料；来源家族、时间、内容 hash；开发集或冻结保留集 |
| 初始状态 | 授权集合、经验与来源版本、当前时间、项目文件、服务状态；明确哪些依赖真实运行、哪些被替换 |
| 历史材料 | 学习器可读的材料、真实来源身份、输入顺序；与后续任务和参考答案分开 |
| 操作序列 | 提交、查询、核实、纠正、重启等实际调用，以及每步允许的工具与终止条件 |
| 必须结果 | 应保留的知识点、行动条件、输出用途、状态变化、最终文件或业务结果；为每项分配 assertionId |
| 禁止结果 | 例如无依据断言、条件未知时直接 guidance、失效建议恢复、无关文件被改动；标明是否为零容忍项 |
| 判定方法 | 每个 assertion 对应程序检查、人工 rubric 或两者；标签版本、评审依据、允许的语义等价表达 |
| 执行与证据 | 初始化/运行/清理入口、时限、重复次数、模型配置、需要保存的响应/状态/产物、预定门槛 |

结构合同可以使用可信的固定经验直接测适用性；完整学习场景必须从材料实际生成经验。两类结果分别标注。不能手工注入正确经验后，把下游通过算成提取质量通过。

参考答案、人工标签和后续任务不传给提炼器。任务执行器只收到实际任务、允许访问的环境和该组正常召回内容；判定器掌握答案。生成文案允许措辞变化，精确标识符、来源归属、会影响行动的条件与例外必须保留。

## 贯穿实现的例子：生成客户端

场景族 `generated-client-lifecycle` 使用[产品示例](01-product.md#一个贯穿实现的例子)：历史调查确认直接修改生成客户端会被覆盖，修改 schema 后生成与检查通过，手写适配器不经过该生成流程。材料限定项目与流程；跨项目复用另设独立样本验证。

下列步骤在隔离环境执行，每一步记录 API 结果、当前状态和必要的文件检查。表中的后续变体属于同一案例家族，不计为多个独立收益样本。

| 步骤与关联验收 | 必须结果与判定 | 失败条件 |
|---|---|---|
| 历史材料提炼：L02、L05 | 人工标签确认形成可复用做法，项目/生成条件与手写例外完整；程序核对摘录和来源 | 把全部客户端概括为生成产物，或补造材料中没有的原因 |
| 适用任务与手写反例：R01、T03 | 中文任务可召回相应英文经验；生成任务修改源文件并重新生成，最终检查通过；手写任务直接维护目标，相关经验不被全局停用 | 改生成产物后无法保留结果；修改无关输入；把本次不适用当全局错误 |
| 当前条件未知再核实：T01、T02、T08 | 首次只返回 lead 和具体缺口；可信工具确认文件来源后 target 重评得到 guidance；核实本身不改变经验 revision 或来源数 | 未核实直接建议；仅凭 Agent 自报条件成立就解除缺口 |
| 新增 legacy 例外：C01、U06、U08 | 提交带新证据的纠正，回执依次符合可靠接收、旧版暂停、新版可用的真实状态；legacy 任务不再使用旧规则 | job completed 就报生效；暂停后更新失败又恢复旧建议；用暂停清空所有经验冒充修订成功 |
| 来源撤回与重新处理：C02、T05、K07、K09 | 从上一状态建立独立副本，撤回该规则全部支持来源；相关经验和依赖它的派生建议不再投递；重启、重处理后重新查验 | 只删除基础记录，派生建议或缓存继续投递；后台再次发布失效规则 |

多来源场景另设变体（K06）：撤回一个来源后，仍有充分独立支持的部分应重新判断并可继续使用，不能靠清空整个库通过删除验收。需要全文清理的显式删除另按 C04 检查副本；来源撤回不自动等同物理删除所有材料。

这个场景的产品合同由各记忆适配器共用。厂商内部 ID、score、bank 或 collection 不作为预期答案；需要验证内部清理时，由后端专用检查提供证据。

## 首批场景与样本管理

先补齐下面八组开发回归。已有两个手写任务可作为第一组的起点；另从 ProvenLoop 的 92 个手写窗口中选择并同步了[48 个开发材料](../evals/README.md)，用于提炼、语义边界与来源角色回归。材料已有完整性校验，尚需输入适配、独立标签、具体后续任务与判定器，不能计为已通过的场景。每组包含相近的正例与反例，先暴露机制错误，再扩充真实样本。

| 场景组 | 首批必须覆盖 | 关联验收 |
|---|---|---|
| 生成客户端生命周期 | 上述学习、采用、核实、纠正、撤回全过程 | L02、R01、C01–C04、T01–T03、U06 |
| 临时要求与长期偏好 | “这次简短”与“以后简短”；制定要求与无依据事实断言；零经验成功与提取失败 | L01、L03、A01–A04、A13 |
| 因果与高层提炼 | 多变量后成功、证据不足的泛化，以及有机制/迁移依据应产出的正例 | L05、L06、D05、A06 |
| 重复、冲突与失效 | 转发/复述不算独立支持；父经验改版；held 到期与补证竞争 | L07、C02、A07、A10 |
| 检索与适用边界 | 中文问英文、精确参数、例外词、无关任务、错误 scope、未知条件 | R01–R05、D01–D03、T04–T06 |
| 写入与恢复 | 明确失败、未知提交、迟到响应、断点重启、删除后恢复 | M05–M08、C03、C04 |
| 宿主与管理入口 | 自动回填、采用前刷新、两会话隔离、失败回执、关闭 UI 后继续学习、安装与重启 | X02、X04–X06、U01–U12 |
| Connector 更新 | 重复页面、部分接收、源修订、撤回、永久忘记、游标与学习状态分离 | X03、K01–K12 |

这些机制样本允许用于调试，不替代[发布所需样本](05-delivery-and-validation.md#质量样本与发布门槛)。发布仍需要规定的学习材料、查询、多层案例和后续任务；组数、同义改写数、重复运行数不能抵充独立样本数。

保留集按时间和来源家族切分。同一家族的原文、转发、改写和后续变体放在同一划分，不能跨开发集与保留集。失败案例加入开发回归时记录出处；已据此调整实现的案例不再作为未见测试，补充新的保留材料。

每个用例、标签、判定器和阈值文件都有版本。确认标签错误时保留原记录、仲裁原因和重评结果，统一重评相关版本，不能只修当前候选的标签。

## 判定与指标口径

程序负责可确定的事实：状态、修订、授权、引用原文、调用次数、文件差异、检查是否发生在最后一次修改之后，以及超时和重启后的结果。来源子串存在不能证明它支持整条结论；模型返回 supported 也不能作为独立证据。

经验语义按“值得保留、支持充分、条件/例外完整、覆盖应学知识点”分别标注，每项为通过、失败或待仲裁，并保留对应来源和理由。待仲裁不折算成半分，不排除出样本以提高准确率；必测结果未仲裁时该项评估阻塞。两位独立评审与仲裁沿用发布要求。模型评委可辅助筛查，记录模型与提示词版本，并用人工标签校准，不能成为唯一发布判据。

| 指标 | 计数单位与分母 |
|---|---|
| 留存价值 | 值得保留的输出条目 / 全部实际保留条目，包含新增 held；需实质重写的条目另列 |
| 重要经验覆盖 | 被正确表达并保留的标注知识点 / 全部应保留知识点；合并卡片不减少分母，重复表达不重复计数 |
| 条件与例外完整 | 正确保留的标注行动限制 / 应保留知识点所需的全部行动限制；漏掉整个知识点也不能从分母移除；另列关键限制缺失次数 |
| 来源支持 | 逐条核对事实/因果断言与来源；列出不受支持的断言数及其所在输出数，用户规范单独标注 |
| Precision@3 | 正确返回项 / 实际返回项；正确项必须同时满足内容、范围和 guidance/lead 用途，先按请求去重，再汇总分子/分母 |
| Recall@3 | 已正确召回的标注核心目标 / 应召回核心目标，每请求提前标注最多 3 个；返回空且应有目标计漏召回 |
| 正确不建议 | 请求正常完成、未返回 guidance/lead 且不建议原因符合标签的请求 / 全部标注应排除请求；超时、服务错误或无有效响应不计入成功分子，另列异常；无相关目标的请求不进入 Recall 分母 |
| 核实与采用 | lead 转为正确 guidance 的次数 / 实际启动的 lead 核实次数；同时列无效检查、超预算和误采用，按任务计入成本 |

召回按当前步骤的标签判断；lead 与 guidance 分开报告，核实前后不在同一个分母里重复计算目标。某指标没有分母时报告 N/A 和原因，不能记为 100%；必需类别缺样本则为 blocked。

后续任务先判完成质量和新增错误，再比较重复工作。代码任务检查最终文件、必要构建/测试及无关变更；其他任务在运行前确定可核验的产物和 rubric。工具调用总数不直接等于重复调查，应按日志和预先定义的调查单元区分重复查找、必要核实及正常工作。

## 对照、重复运行与引擎更换

对照保持相同模型、历史材料、任务环境、工具权限、宿主原生记忆和项目指令。基础组采用引擎合理的原生配置；LessonLoop 组增加产品准入与使用规则。分别比较“有无额外记忆”和“相同引擎有无领域层”，避免把底座变化与领域规则变化混在一个差值里。

当前三组入口是 no_memory、mem0_default、structured_learning。以后接入 Hindsight 时，按同样方式增加基础 Hindsight 与 LessonLoop/Hindsight。能力差异、实际生效的模型参数和召回预算写入配置清单；同一轮实验不能为了某组结果好看而临时修改。Hindsight 尚未验收，不能引用 Mem0 的运行结果作为它的质量结论。

开发阶段的真实模型场景默认每任务、每组独立运行 3 次，用于发现波动；这个次数不构成发布所需统计把握。发布前固定任务数、重复次数、顺序、预算和非劣化判据，并满足[后续任务收益](05-delivery-and-validation.md#后续任务收益)要求。报告逐任务配对差值、通过/失败分布与不确定性，重复运行仍按同一任务聚合，不能作为独立用户样本。

完整评测每次从干净环境与独立记忆重新学习，使用固定的历史时间顺序；不把上一组或上一轮结果写入下一轮。排查召回时可以另跑固定经验快照，但注明只测召回。Agent 的任务检查反馈属于正常工具结果，其他组的答案和评委解释不得注入。

记录提取、整理、嵌入、检索、核实、执行和维护的全部调用与耗时，分别报告冷启动和复用后的摊销。订阅模型也记录 token 与配额使用；某引擎内部用量拿不到时标记缺失，不填零、不作完整成本优势结论。模型调用量按当前选型约束用于诊断和预算管理，质量与用户收益分别判断。

任务失败、超时和异常保留在计划样本清单中。按预定规则重试时同时保留初次结果、原因和重试次数，不能只取最好一次。性能统计保留失败率与超时，未完成请求不得悄悄从延迟样本中移除。

## 评估状态与退出码

以下是待实现的评测报告合同，字段与退出码不描述现有所有脚本的行为。它们属于开发工具，与产品学习作业的 status 和 receipt 无关。

profile 是一次评测的范围清单，固定阶段、后端/宿主、场景、必测项、依赖和阈值版本，例如某后端的合同回归或首版发布验收。运行前冻结该清单，报告保留其版本；不同范围的结果不能共用一个无范围说明的“通过”。

runStatus 表示执行过程：completed 是计划运行结束，error 是执行器或依赖发生异常，blocked 是缺前提而无法开始或完成必测步骤。gateStatus 表示判定：passed、failed 或 blocked。正常跑完全部任务可以同时得到 completed 和 failed。

| 情况 | gateStatus | 评测命令退出码 |
|---|---|---|
| 所选 profile 的必测断言、必需样本与标签齐全，并达到冻结门槛 | passed | 0 |
| 已观察到硬合同违规、零容忍错误或已完成指标未达门槛 | failed | 1 |
| 无已确认质量失败，但必测依赖、实现、样本、标签或结果缺失 | blocked | 2 |

聚合顺序为 failed 优先于 blocked，全部必测齐全且通过才为 passed；失败与未测清单同时保留。执行器或基础设施异常先记录 runStatus=error，若没有足够证据证明产品违规则 gateStatus=blocked；被测服务在预定故障场景中违反恢复合同则为 failed。

任务对照中的某次失败记录为该组的任务结果，按预先冻结的产品质量和收益门槛聚合；基础组失败不自动阻断候选，也不自动证明候选有效。候选的错 scope、已知旧版投递等零容忍违规仍立即使门禁失败。不能用“所有对照组的每次任务都必须成功”代替收益评测。

每次运行至少输出一份可机器读取的报告和一份简短的审阅摘要，包含：

- runId、profile、代码 revision 与工作区差异 hash、数据/标签/判定器/阈值版本、命令、时间、平台及实际依赖/模型配置。
- 计划场景清单、适用验收 ID、每个 assertion 的预期/实际/状态、运行次数、判定依据、脱敏证据位置和产物 hash。
- 各项指标的分子分母、任务配对结果、延迟分布、失败/超时、全部可测成本，以及缺失值和限制。
- runStatus、gateStatus、失败列表、必测未完成列表、对上一个冻结版本新增/消失的回归，以及重跑记录。

诊断项和不适用项在运行前声明；必测项不能事后改为 skipped。CI 只在所选 profile 为 passed 时显示通过。局部 profile 通过须显示范围，不能外推为发布通过。报告保留必要的短摘录与产物，沿用材料授权和脱敏范围，不把原始私有会话或凭据提交到仓库。

## 开发与发布怎样使用

| 时机 | 执行范围 | 完成要求 |
|---|---|---|
| 修改文档 | 文档结构、链接、示例与验收交叉引用 | 新要求能找到场景与判定规则；标明未实现部分 |
| 修改确定性逻辑 | 类型、相关单测与合同回归；涉及状态或存储时增加真实后端及受影响故障场景 | 关联 assertion 通过，失败修复保留最小回归；不为无关低影响改动增加重复测试 |
| 修改提炼/检索提示词、模型、排序、嵌入或引擎 | 相关开发语义集、召回集及重复运行，与冻结版本逐例比较 | 记录收益、退化和标签分歧；通过样例不能替代冻结集 |
| 修改宿主、CLI/UI、同步或打包 | 对应真实环境端到端路径、恢复和回执 | 模拟器结果与真实宿主结果分别列出 |
| 阶段退出与发布候选 | 该阶段完整合同；发布另跑保留集、真实任务对照、性能、安装和恢复 | 必测无缺项，达到实施与验收的门槛；任何已知零容忍违规阻断发布 |

阶段依赖按 P0–P4 声明。UI、样例 Connector 纳入 P3 首版验收，真实来源 Connector 按 P4 单独交付；未到阶段的工作列为计划项，到对应交付时必须进入必测清单。模型额度不足时，继续完成不依赖模型的检查，把对应模型 profile 留为 blocked。

代码评审附上变更对应的验收 ID、scenarioId/assertionId、实际运行入口与报告，以及尚未验证的范围。评审者从一个关键正常路径和一个失败/例外路径核对“要求 → 测试 → 证据”，并检查是否存在跳过真实实现、泄漏答案或过弱判定器。

实现评测门禁本身时，用一个已知通过结果、一个已知断言失败结果和一个必测缺失结果检查报告及退出码；给判定器一个错误最终产物，确认它不会仅凭 Agent 自报成功而通过。

## 当前入口与落实顺序

以下状态依据 2026-09-14 的仓库检查。既有实测结果见[P0 记录](research/2026-09-13-p0/README.md)，本次文档补充没有增加模型或引擎实测。

| 已有入口 | 覆盖与限制 |
|---|---|
| `node scripts/validate-eval-corpus.mjs` | 48 个开发材料、92 项来源选择与 16/48 材料子集的结构/hash/引用校验；不执行模型、任务或质量门禁 |
| `npm run validate:docs` | 文档结构、链接、JSON 和引文范围；不检查设计语义、运行结果或评测达标 |
| `npm run typecheck`、`npm test` | 类型与局部测试；最近检查 23/23 单测通过，不是完整验收目录覆盖率 |
| `npm run p0:storage` | 真实 Mem0/Qdrant/本地嵌入的小样本探针；未知写入恢复及候选限额前过滤压力仍缺覆盖 |
| `npm run p0:host`、`npm run p0:host-hooks` | 隔离 CLI 与脚本模型协议探针；不包含真实 Agent 使用收益和完整安装体验 |
| `npm run p0:evaluate` | 两个手写任务、三组对照入口；真实模型结果尚为 blocked，完整准入、lead 核实、独立标签、重复评测和完整成本未实现 |

[现有评测代码](../spikes/p0/evaluate.ts)会保存任务的 passed，但正常结束仍可返回 status=completed 和退出 0；它尚未按质量结果计算门禁。未配置模型的路径退出 2。当前 status 字段不能直接当作 gateStatus，接 CI 前先补判定与失败传播。

落实顺序：

1. 为当前两例补齐场景身份、关联验收和独立判定；实现报告、profile 和门禁聚合，验证已知失败与缺项会阻断。
2. 使用已同步材料扩展八组开发场景，把固定经验的结构测试与真实学习任务分开；优先补独立 oracle、当前状态和后续产物，逐项标明缺少的实现和测试入口。
3. 在已有类型/单测基础上接入 CI；真实后端、真实模型和宿主各有明确入口与依赖，不配置依赖的 CI 不能冒充全量通过。
4. 准备获准使用的真实材料和独立标签，冻结保留集；运行规定规模的质量与收益评测，再以相同产品合同验收新的记忆适配器。

[evals](../evals/README.md) 已保存材料、来源选择和 16/48 子集；标签、任务判定器与阈值配置后续在此补齐，与 P0 探针分开。运行产物按 runId 放在工作区隔离输出目录。材料选择配置不等于可执行评测 profile，完整评测命令和 CI 仍待实现。
